# How other macOS apps draw a volume pop-up that replaces the system one

Researched 2026-10-25. Question: Isla's volume pop-up lags behind the key while its brightness pop-up does not. How do other apps intercept the volume keys, set the level, decide what number to draw, watch for outside changes and keep the system OSD quiet, and what in that is shared by the ones that do not lag?

Read-only research. No app was launched, nothing was measured, no Isla file was changed. Source was read at the commits named in each section (GitHub `main`/`develop` as of 2026-10-25). Line numbers are for those commits; permalinks are given so they stay true. Where a claim comes from a search-result snippet that I did not open, it says so.

**Headline limit: no project below publishes a key-to-pixel latency figure, and I did not measure one.** The only latency number in any source is Atoll's, for something else (looking up a process id: 0.6 ms against 67 ms for `pgrep`). "Fast" in the last section therefore means "designed so the slow step is off the path", read from code and comments, not "measured fast".

## 1. Apple's own behaviour

- **Steps.** The classic OSD is 16 segments: MonitorControl, which draws through Apple's OSD API, sets `chicletCount = 16` and passes `filledChiclets`/`totalChiclets` to `showImage` ([OSDUtils.swift L38 and L69](https://github.com/MonitorControl/MonitorControl/blob/7cfe64500d19cbbcbf82121a91c826f658a403bd/MonitorControl/Support/OSDUtils.swift#L25-L40)). Option+Shift moves in smaller steps: Apple's own wording is only "smaller steps", no fraction ([Mac keyboard shortcuts, Finder and system shortcuts](https://support.apple.com/en-us/102650)). The 1/16 and 1/64 figures are third-party readings of the system: volumeHUD's constants `standardStep = 1/16` ("matching macOS default") and `fineStep = 1/64` ([MediaKeyInterceptor.swift L98-L102](https://github.com/dannystewart/volumeHUD/blob/ceb8939997cc93ed0c917254f4cf3d147088b966/volumeHUD/MediaKeyInterceptor.swift#L98-L102)), boring.notch's `step = 1/16` with a divisor of 4 for Option+Shift ([MediaKeyInterceptor.swift L30 and L200](https://github.com/TheBoredTeam/boring.notch/blob/23e7705a4ffcb5d97a54fb1d4135e180084a566d/boringNotch/observers/MediaKeyInterceptor.swift#L199-L224)), and Atoll. I found no Apple document that states 1/64.
- **Key-down, and the repeat bit.** The media-key event is a system-defined subtype-8 event; `data1` carries the key code in the high 16 bits, the state in bits 8-15 (0xA down, 0xB up) and a repeat flag in bit 0 ([MediaKeyTap NSEventExtensions.swift L20-L26](https://github.com/MonitorControl/MediaKeyTap/blob/22293b608bb9e7072960a2002d77ebbbdb3ba859/MediaKeyTap/NSEventExtensions.swift#L20-L26)). Every interceptor below acts on 0xA only (key-up is passed or swallowed unused). I found no Apple text saying the OSD itself reacts on key-down; that is inferred from the fact that a swallowed key-down is enough to stop it in boring.notch and volumeHUD.
- **A write is not instant at the device.** Apple's CoreAudio header, on `AudioObjectSetPropertyData`: "the value of the property should not be considered changed until the HAL has called the listeners as many properties values are changed asynchronously" (`AudioHardware.h` L302-L303 in the Xcode 27.1 SDK, `/Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/System/Library/Frameworks/CoreAudio.framework/Headers/AudioHardware.h`). Same header, `AudioObjectAddPropertyListenerBlock`: with a NULL queue "the block will be directly invoked" (L389), that is on the HAL's thread, not the main thread. So a pop-up that waits for the listener inherits the device's latency (Bluetooth, USB, HDMI) plus a thread hop. That consequence is my reading of the header; no source measures it.
- **An unresponsive tap is switched off.** `CGEvent.h` L322-L325: "If a tap becomes unresponsive ... an appropriate `kCGEventTapDisabled...` event is passed to the registered CGEventTapCallBack", and the tap can be re-enabled with `CGEventTapEnable`. The callback "runs from the CFRunLoop to which the tap CFMachPort is added" (L290-L293), so which thread the tap lives on is the app's choice.
- **macOS 26 and 27 presentation.**
  - 26 replaced the 16-segment bezel with a small popover in the screen corner (volumeHUD's stated reason to exist, [README](https://github.com/dannystewart/volumeHUD/blob/ceb8939997cc93ed0c917254f4cf3d147088b966/README.md); Many Tricks' Hudlum says the same, [manytricks.com/hudlum](https://manytricks.com/hudlum)).
  - MonitorControl 4.4.0 (2026-09-15, "macOS 26 and 27 compatibility") still talks to the classic helper on 26 and 27: it opens an `NSXPCConnection` to the mach service `com.apple.OSDUIHelper` ([OSDUtils.swift L61-L67 and L84-L146, mach name at L104](https://github.com/MonitorControl/MonitorControl/blob/7cfe64500d19cbbcbf82121a91c826f658a403bd/MonitorControl/Support/OSDUtils.swift#L61-L146); [commit fa7ed0a](https://github.com/MonitorControl/MonitorControl/commit/fa7ed0abef68c3e5320936259779775f22d40dbb)).
  - Its maintainer says that on 27.0 the native UI is called through Control Center, that Apple changed it again in 27.2, that it is "not a public/stable API", and that he will not follow it ([MonitorControl #1904](https://github.com/MonitorControl/MonitorControl/issues/1904)). BetterDisplay's 27.2 work adds the new rounded segmented OSD and mentions reducing "interference from macOS Control Center when the app is busy" ([v5.1.1 notes](https://github.com/waydabber/BetterDisplay/releases/tag/v5.1.1)), and removed a "Forced System OSD" option on 27 as no longer working ([v4.3.5](https://github.com/waydabber/BetterDisplay/releases/tag/v4.3.5), #5612).
  - Atoll still SIGSTOPs `OSDUIHelper` on current builds (section 2.5), so that helper process exists on the Macs its users run; I did not test on 27.x which process draws the OSD there.

## 2. Open-source projects

Summary matrix first; details, with the evidence, follow.

| | Tap location, options | Tap thread | Swallows | Set volume with | Number shown | Outside changes | System OSD |
|---|---|---|---|---|---|---|---|
| boring.notch | HID, head, default | main run loop | key-down only (key-up passes) | `VolumeScalar` main, else elements 1-4; sync on main | target just computed, before any read-back | listener (NULL queue) then re-read, async to main | swallowed |
| Atoll | HID, else session; head, default | main run loop | key-down and key-up | `VolumeScalar` per element, else `VirtualMainVolume`; on main | the value just written (cached), via listener callback too | listeners on a private serial queue | swallowed and `killall -STOP OSDUIHelper` |
| mew-notch | session, head, default | thread that called `start()` | key-down and key-up | `VirtualMainVolume`; inside the tap callback | from the listener (read-back) | listener to `performSelectorOnMainThread` | swallowed |
| volumeHUD | HID, head, default | main run loop | key-down only | `VirtualMainVolume`; on main actor | quantized expected value, not the read-back | listeners on main queue + device-change timer | swallowed |
| SlimHUD | none (MediaKeyTap observes through `sendEvent`) | n/a | no | does not set | AppleScript read after the key, plus a 0.2 s poll | distributed notification + 0.2 s poll | `killall -STOP OSDUIHelper`, repeated every 60 s |
| MonitorControl | session, head, default (MediaKeyTap) | own thread, then `main.sync` | key-down and key-up, only for keys it needs | DDC write, coalesced, off main; for audio it steps aside | cached value, drawn before the write lands | n/a for DDC | Apple's own OSD via private API |

### 2.1 boring.notch (TheBoredTeam, GPL, very active)

Read at [`23e7705`](https://github.com/TheBoredTeam/boring.notch/tree/23e7705a4ffcb5d97a54fb1d4135e180084a566d).

- **Interception.** `CGEvent.tapCreate(tap: .cghidEventTap, place: .headInsertEventTap, options: .defaultTap, eventsOfInterest: 1 << 14, ...)`, source added to `CFRunLoopGetMain()` in `.commonModes` ([MediaKeyInterceptor.swift L67-L88](https://github.com/TheBoredTeam/boring.notch/blob/23e7705a4ffcb5d97a54fb1d4135e180084a566d/boringNotch/observers/MediaKeyInterceptor.swift#L67-L88)). The callback converts to `NSEvent`, takes key-down only (0xA), returns `nil` for the keys it owns ([L103-L139](https://github.com/TheBoredTeam/boring.notch/blob/23e7705a4ffcb5d97a54fb1d4135e180084a566d/boringNotch/observers/MediaKeyInterceptor.swift#L103-L139)). Key-up is passed through. There is no `tapDisabledByTimeout` branch in the file.
- **Repeat.** No repeat handling in the file; every key-down event, repeats included, is one step.
- **Work.** The callback only schedules `Task { @MainActor in ... }` ([L199-L224](https://github.com/TheBoredTeam/boring.notch/blob/23e7705a4ffcb5d97a54fb1d4135e180084a566d/boringNotch/observers/MediaKeyInterceptor.swift#L199-L224)). Before each volume step it plays the feedback sound (`AVAudioPlayer`) when the system preference is on (L204-L207, L178-L197), then reads and writes CoreAudio on the main actor.
- **Setting the level.** `increase`/`decrease` read the device ("average of main and channels 1-4", [VolumeManager.swift L224-L233](https://github.com/TheBoredTeam/boring.notch/blob/23e7705a4ffcb5d97a54fb1d4135e180084a566d/boringNotch/managers/VolumeManager.swift#L224-L233)), add the step, call `setAbsolute`, which writes `kAudioDevicePropertyVolumeScalar` on the main element and falls back to elements 1-4 ([L87-L101, L235-L257](https://github.com/TheBoredTeam/boring.notch/blob/23e7705a4ffcb5d97a54fb1d4135e180084a566d/boringNotch/managers/VolumeManager.swift#L87-L101)). All synchronous, on main.
- **What is drawn.** The target value, immediately after the write call returns and without waiting for any listener: `toggleSneakPeek(status: true, type: .volume, value: CGFloat(target))` ([L37-L53](https://github.com/TheBoredTeam/boring.notch/blob/23e7705a4ffcb5d97a54fb1d4135e180084a566d/boringNotch/managers/VolumeManager.swift#L37-L53)). The show is a `withAnimation(.smooth)` state flip and a hide task of 1.5 s that is cancelled and restarted per press ([BoringViewCoordinator.swift L208-L260](https://github.com/TheBoredTeam/boring.notch/blob/23e7705a4ffcb5d97a54fb1d4135e180084a566d/boringNotch/BoringViewCoordinator.swift#L208-L260)).
- **Brightness differs.** It is `await client.currentScreenBrightness()` then `await client.setScreenBrightness(target)` over an XPC helper, and only after the set succeeds does it publish and draw ([BrightnessManager.swift L30-L42](https://github.com/TheBoredTeam/boring.notch/blob/23e7705a4ffcb5d97a54fb1d4135e180084a566d/boringNotch/managers/BrightnessManager.swift#L30-L42)). So in this app the brightness path waits for the device and the volume path does not, the opposite of Isla's.
- **Outside changes.** Listeners on the default device, `VolumeScalar` (main element, else channels 1-2) and mute, registered with a NULL queue ([VolumeManager.swift L172-L222](https://github.com/TheBoredTeam/boring.notch/blob/23e7705a4ffcb5d97a54fb1d4135e180084a566d/boringNotch/managers/VolumeManager.swift#L172-L222)). The block re-reads every element and publishes through `DispatchQueue.main.async`. Our own write also triggers this listener; it is a refresh, not what the user sees first.
- **System OSD.** Only the swallow; there is no process-level suppression in the file. Related reports: the HUD stops until toggled off and on after sleep or a user switch, and the system OSD does not come back after turning it off ([#898](https://github.com/TheBoredTeam/boring.notch/issues/898)); the half-step setting of a key remapper is ignored because the app applies its own 1/16 ([#1428](https://github.com/TheBoredTeam/boring.notch/issues/1428)).
- **Lag-related work.** None merged that I found. Open [PR #1540](https://github.com/TheBoredTeam/boring.notch/pull/1540) (2026-09-14, "Keep volume commands tied to the current audio route") says: "Keep one accepted physical write with coalesced newer intent while hardware acknowledgement is pending. A bounded reconciliation deadline prevents missing notifications from permanently blocking later input," and cites AirPods and DAC devices ([#1433](https://github.com/TheBoredTeam/boring.notch/issues/1433), [#961](https://github.com/TheBoredTeam/boring.notch/issues/961)). Its author notes physical AirPods/DAC behaviour is unverified. Treat it as a design under review, not a shipped fix.

### 2.2 Atoll (Ebullioscopic, GPL, forked from boring.notch, very active)

Read at [`3a16b4f`](https://github.com/Ebullioscopic/Atoll/tree/3a16b4fe32db4a705a1db4a09642419a7a442d79). The most carefully commented of the set.

- **Interception.** Tries `.cghidEventTap`, then `.cgSessionEventTap`, `.headInsertEventTap`, `.defaultTap`, mask system-defined only, on the main run loop ([managers/MediaKeyInterceptor.swift L148, L184-L235](https://github.com/Ebullioscopic/Atoll/blob/3a16b4fe32db4a705a1db4a09642419a7a442d79/DynamicIsland/managers/MediaKeyInterceptor.swift#L184-L235)). Swallows the key-down and, when intercepting that key, the key-up too ([L355-L361](https://github.com/Ebullioscopic/Atoll/blob/3a16b4fe32db4a705a1db4a09642419a7a442d79/DynamicIsland/managers/MediaKeyInterceptor.swift#L355-L361)). Re-enables the tap on `tapDisabledByTimeout` and `tapDisabledByUserInput` and immediately re-suppresses the native OSD ([L326-L338](https://github.com/Ebullioscopic/Atoll/blob/3a16b4fe32db4a705a1db4a09642419a7a442d79/DynamicIsland/managers/MediaKeyInterceptor.swift#L326-L338)). Retries tap creation every 2 s for 30 tries, then every 15 s, for up to an hour, since `tapCreate` fails until Accessibility is granted ([L67-L94, L237-L293](https://github.com/Ebullioscopic/Atoll/blob/3a16b4fe32db4a705a1db4a09642419a7a442d79/DynamicIsland/managers/MediaKeyInterceptor.swift#L67-L94)).
- **Stated rule.** "Keep all potentially blocking CoreAudio/CoreBrightness work outside the event-tap callback. A tap callback must return promptly or macOS disables it and the next media key falls through to the native OSD" ([L389-L391](https://github.com/Ebullioscopic/Atoll/blob/3a16b4fe32db4a705a1db4a09642419a7a442d79/DynamicIsland/managers/MediaKeyInterceptor.swift#L389-L408)). It does this by `DispatchQueue.main.async` to the delegate. `isRepeat` is decoded (L351) and passed but unused in the volume handler ([SystemChangesObserver.swift L185-L209](https://github.com/Ebullioscopic/Atoll/blob/3a16b4fe32db4a705a1db4a09642419a7a442d79/DynamicIsland/managers/SystemChangesObserver.swift#L185-L209)).
- **Setting the level.** `SystemVolumeController.adjust(by:)` reads the current level, adds the step, and `setVolume` writes `VolumeScalar` per settable element, falling back to `VirtualMainVolume` (`0x766D7663`, "The property macOS's own volume UI works through") ([managers/SystemMediaControllers.swift L90-L95, L148-L171, L196-L248](https://github.com/Ebullioscopic/Atoll/blob/3a16b4fe32db4a705a1db4a09642419a7a442d79/DynamicIsland/managers/SystemMediaControllers.swift#L148-L248)). It refuses to step from a level it never confirmed on that device (L165-L168) and keeps the last written value per device "until a read says otherwise" so a failed read after the write cannot snap the bar back (L233-L247).
- **What is drawn.** `notifyCurrentState()` right after the write (L247) calls `onVolumeChange`, which draws the held value ([SystemChangesObserver.swift L102-L108, L259-L307](https://github.com/Ebullioscopic/Atoll/blob/3a16b4fe32db4a705a1db4a09642419a7a442d79/DynamicIsland/managers/SystemChangesObserver.swift#L102-L108)). That is the written value, not an independent read. The same callback fires for outside changes.
- **Brightness, with the longest comment on the subject.** `adjust(by:)` accumulates onto a `pendingAdjustTarget` (or the in-flight animation target, or the last emitted value) instead of asking the system, then hops to main once: "Do not synchronously query CoreBrightness/DisplayServices here. This method is reached from hardware-key handling, and those calls can be slow enough for macOS to disable the event tap" ([SystemMediaControllers.swift L713-L729](https://github.com/Ebullioscopic/Atoll/blob/3a16b4fe32db4a705a1db4a09642419a7a442d79/DynamicIsland/managers/SystemMediaControllers.swift#L713-L729)). Emissions during an animation are throttled and the final value is forced ([L854-L876](https://github.com/Ebullioscopic/Atoll/blob/3a16b4fe32db4a705a1db4a09642419a7a442d79/DynamicIsland/managers/SystemMediaControllers.swift#L854-L876)). The volume path has no equivalent accumulator; it reads the device each press.
- **Outside changes.** Listeners on the default device and on the volume/mute elements, delivered on a private serial queue `com.dynamicisland.volume-listener` ([SystemMediaControllers.swift L69, L294-L360](https://github.com/Ebullioscopic/Atoll/blob/3a16b4fe32db4a705a1db4a09642419a7a442d79/DynamicIsland/managers/SystemMediaControllers.swift#L294-L360)).
- **System OSD.** Swallow plus a freeze of the helper: `suppressNativeOSDNow()` is called on every volume, mute and brightness command and on every volume callback; its comment says "The CoreAudio volume write wakes/respawns the helper to draw the native OSD (brightness's private APIs never do), and the watcher can lose that race" ([SystemOSDManager.swift L228-L267](https://github.com/Ebullioscopic/Atoll/blob/3a16b4fe32db4a705a1db4a09642419a7a442d79/DynamicIsland/managers/SystemOSDManager.swift#L228-L267)). It runs `Task.detached(priority: .userInitiated)`, first looks the helper up by sysctl (`osduiHelperPID`) and skips if that pid was already stopped, otherwise forks `killall -STOP OSDUIHelper` ([L492-L503](https://github.com/Ebullioscopic/Atoll/blob/3a16b4fe32db4a705a1db4a09642419a7a442d79/DynamicIsland/managers/SystemOSDManager.swift#L488-L503)). A 150 ms watcher catches respawns because macOS exits the helper when idle ([L371-L382](https://github.com/Ebullioscopic/Atoll/blob/3a16b4fe32db4a705a1db4a09642419a7a442d79/DynamicIsland/managers/SystemOSDManager.swift#L371-L382)); the pid lookup is measured in a comment: "67ms of wall time and ~5ms of CPU" for `pgrep` against 0.6 ms from the kernel (L444-L449; [PR #767](https://github.com/Ebullioscopic/Atoll/pull/767)). The freeze has costs the project has had to fix: the helper stayed frozen after quit and broke keyboard-backlight and external-display OSDs ([#568](https://github.com/Ebullioscopic/Atoll/issues/568), [PR #569](https://github.com/Ebullioscopic/Atoll/pull/569), [#574](https://github.com/Ebullioscopic/Atoll/issues/574)), and an open report of the native volume HUD freezing in place beside Atoll's ([#608](https://github.com/Ebullioscopic/Atoll/issues/608)).
- **Feedback sound.** Off the key path and rate-limited: serial queue, minimum 80 ms between plays ([SystemChangesObserver.swift L430-L453](https://github.com/Ebullioscopic/Atoll/blob/3a16b4fe32db4a705a1db4a09642419a7a442d79/DynamicIsland/managers/SystemChangesObserver.swift#L430-L453)).
- **Also present, not on the HUD path:** `SystemVolumeManager` reads via AppleScript `output volume of (get volume settings)`, copied from SlimHUD ([SystemVolumeManager.swift L21-L44](https://github.com/Ebullioscopic/Atoll/blob/3a16b4fe32db4a705a1db4a09642419a7a442d79/DynamicIsland/managers/SystemVolumeManager.swift#L21-L44)); the observer uses `SystemVolumeController`, not this.

### 2.3 mew-notch (monuk7735, GPL, active)

Read at [`8377111`](https://github.com/monuk7735/mew-notch/tree/8377111cd9742c9612930688a78e5fce5056d30c).

- **Interception.** `.cgSessionEventTap`, head, `.defaultTap`, mask system-defined + key-down + key-up, run-loop source on `CFRunLoopGetCurrent()` (whatever thread called `start()`) ([MediaKeyManager.swift L29-L58](https://github.com/monuk7735/mew-notch/blob/8377111cd9742c9612930688a78e5fce5056d30c/MewNotch/Utils/Managers/MediaKeyManager.swift#L29-L58)). Returns `nil` on key-down and on key-up when the HUD is enabled ([L106-L108, L114-L165](https://github.com/monuk7735/mew-notch/blob/8377111cd9742c9612930688a78e5fce5056d30c/MewNotch/Utils/Managers/MediaKeyManager.swift#L114-L165)); re-enables on timeout (L72-L77). Brightness yields to BetterDisplay when it is running (L133-L135).
- **Setting the level.** Inside the tap callback, synchronously: read `AudioOutput.volume`, add the step, assign `AudioOutput.volume` ([L167-L176](https://github.com/monuk7735/mew-notch/blob/8377111cd9742c9612930688a78e5fce5056d30c/MewNotch/Utils/Managers/MediaKeyManager.swift#L167-L176)). `AudioOutput` reads and writes `kAudioHardwareServiceDeviceProperty_VirtualMainVolume`, retrying once on a bad-object error ([AudioOutput.m L116-L155, L198-L210](https://github.com/monuk7735/mew-notch/blob/8377111cd9742c9612930688a78e5fce5056d30c/MewNotch/Utils/Helpers/AudioControl/AudioOutput.m#L116-L155)).
- **What is drawn.** Driven by the listener: `AudioDeviceVolumeListener` calls `performSelectorOnMainThread:waitUntilDone:NO`, which posts `AudioOutputVolumeNotification` ([L22-L57, L312-L330](https://github.com/monuk7735/mew-notch/blob/8377111cd9742c9612930688a78e5fce5056d30c/MewNotch/Utils/Helpers/AudioControl/AudioOutput.m#L22-L57)). I did not trace the subscriber; the HUD being driven by that notification is my reading. This is the read-back-driven design in the set.

### 2.4 volumeHUD (dannystewart, MIT, feature-complete, 397 stars)

Read at [`ceb8939`](https://github.com/dannystewart/volumeHUD/tree/ceb8939997cc93ed0c917254f4cf3d147088b966). A whole app whose only job is this, and the one with the most explicit handling of hardware quantization.

- **Interception.** HID tap, head, `.defaultTap` ("Important: .defaultTap allows consuming events"), main run loop ([MediaKeyInterceptor.swift L146-L173](https://github.com/dannystewart/volumeHUD/blob/ceb8939997cc93ed0c917254f4cf3d147088b966/volumeHUD/MediaKeyInterceptor.swift#L146-L173)). Key-down only; key-up passes. Modifiers are read three ways (NSEvent, CGEvent flags, `CGEventSource.flagsState`) because any one can miss Option/Shift ([L245-L257](https://github.com/dannystewart/volumeHUD/blob/ceb8939997cc93ed0c917254f4cf3d147088b966/volumeHUD/MediaKeyInterceptor.swift#L245-L257)). The callback is `nonisolated`, hops with `Task { @MainActor }`, returns `nil` ([L220-L298](https://github.com/dannystewart/volumeHUD/blob/ceb8939997cc93ed0c917254f4cf3d147088b966/volumeHUD/MediaKeyInterceptor.swift#L220-L298)).
- **Safety valve.** README: after a key press it checks the level actually changed; if not it assumes interception is not working and stops intercepting until a device change or restart, so the keys never go dead ([README, "Usage"](https://github.com/dannystewart/volumeHUD/blob/ceb8939997cc93ed0c917254f4cf3d147088b966/README.md)).
- **Setting the level.** `VirtualMainVolume`, `AudioObjectSetPropertyData`, then one read to return the actual result ([L404-L427](https://github.com/dannystewart/volumeHUD/blob/ceb8939997cc93ed0c917254f4cf3d147088b966/volumeHUD/MediaKeyInterceptor.swift#L404-L427)). It keeps `volumeControlState` (requested value and its read-back): while the device still reports the physical result of the previous request it steps from the requested value, otherwise from the fresh read, because "some devices map 1/16 targets to different hardware-supported values" ([L89-L90, L489-L501](https://github.com/dannystewart/volumeHUD/blob/ceb8939997cc93ed0c917254f4cf3d147088b966/volumeHUD/MediaKeyInterceptor.swift#L489-L501)). Mutes explicitly at 0 and unmutes when stepping up from mute (L511-L541).
- **What is drawn.** "Show our HUD with the quantized expected value (not the actual read-back). This ensures clean 1/16 or 1/64 steps without partial bar flicker" ([L546-L549](https://github.com/dannystewart/volumeHUD/blob/ceb8939997cc93ed0c917254f4cf3d147088b966/volumeHUD/MediaKeyInterceptor.swift#L546-L549)). It stamps `lastVolumeChangeTime` so `VolumeMonitor` skips the HUD for the change it caused (L543-L544).
- **Outside changes.** `VolumeMonitor` has property listeners on the main queue (L764-L788), and, for when interception is off, listen-only taps at both session and HID level plus an `NSEvent` global monitor (L353, L406-L409, L472-L475; [VolumeMonitor.swift](https://github.com/dannystewart/volumeHUD/blob/ceb8939997cc93ed0c917254f4cf3d147088b966/volumeHUD/VolumeMonitor.swift)). Changelog: a 50 ms deduplication window when several taps fire, automatic recovery when a tap is disabled, duplicate taps prevented ([CHANGELOG.md L17-L18, L164, L175-L176](https://github.com/dannystewart/volumeHUD/blob/ceb8939997cc93ed0c917254f4cf3d147088b966/CHANGELOG.md)).
- **System OSD.** Swallowing the key is the whole mechanism ("volumeHUD hides the system HUD. It does this by intercepting the volume/brightness keys"). Without Accessibility the system HUD shows beside it ([README](https://github.com/dannystewart/volumeHUD/blob/ceb8939997cc93ed0c917254f4cf3d147088b966/README.md)).

### 2.5 SlimHUD (AlexPerathoner, active until June 2026, 468 stars)

Read at [`48a5ae3`](https://github.com/AlexPerathoner/SlimHUD/tree/48a5ae387497c40722b997b994d7aec55b7832c5). The slow design, with its own issue history.

- **Interception.** None. The key is observed (`KeyPressObserver.sendEvent` override and a `MediaKeyTap` with `.keyDownAndUp`) and the system still handles it ([Services/KeyPressObserver.swift L16-L27, L45-L50, L53-L66](https://github.com/AlexPerathoner/SlimHUD/blob/48a5ae387497c40722b997b994d7aec55b7832c5/SlimHUD/Services/KeyPressObserver.swift#L16-L66)). The library is the maintainer's fork of MonitorControl's MediaKeyTap; I read the upstream file (below), not the fork.
- **What is drawn.** After the key notification, `showVolumeHUD` asks AppleScript for `output muted` and `output volume` of `get volume settings` on the main thread, then shows, with a 1.5 s dismiss ([Services/Displayer.swift L47-L62](https://github.com/AlexPerathoner/SlimHUD/blob/48a5ae387497c40722b997b994d7aec55b7832c5/SlimHUD/Services/Displayer.swift#L47-L62); [VolumeManager.swift L13-L33](https://github.com/AlexPerathoner/SlimHUD/blob/48a5ae387497c40722b997b994d7aec55b7832c5/SlimHUD/Services/VolumeManager.swift#L13-L33)). The runner carries a `// TODO: should run in background` on `executeAndReturnError` ([AppleScriptRunner.swift L16](https://github.com/AlexPerathoner/SlimHUD/blob/48a5ae387497c40722b997b994d7aec55b7832c5/SlimHUD/Services/AppleScriptRunner.swift#L16)). A 0.2 s timer also polls volume the same way, and observes `com.apple.sound.settingsChangedNotification` ([ChangesObserver.swift L49-L68, L122-L132](https://github.com/AlexPerathoner/SlimHUD/blob/48a5ae387497c40722b997b994d7aec55b7832c5/SlimHUD/Services/ChangesObserver.swift#L49-L68)).
- **System OSD.** Not swallowed, so it is frozen: `launchctl kickstart gui/<uid>/com.apple.OSDUIHelper`, 0.5 s sleep, `killall -STOP OSDUIHelper` ([Services/OSDUIManager.swift L24-L40](https://github.com/AlexPerathoner/SlimHUD/blob/48a5ae387497c40722b997b994d7aec55b7832c5/SlimHUD/Services/OSDUIManager.swift#L24-L40)), repeated on wake, lid, display change and every 60 s because "sometimes the macOS Huds still show up randomly" ([SystemObserver.swift L58-L62](https://github.com/AlexPerathoner/SlimHUD/blob/48a5ae387497c40722b997b994d7aec55b7832c5/SlimHUD/Services/SystemObserver.swift#L58-L62)). The kickstart comment: "When macOS boots, OSDUIHelper does not start until a volume button is pressed."
- **Issues.** [#86](https://github.com/AlexPerathoner/SlimHUD/issues/86): bars arrived "multiple seconds" late for an `.accessory` app; the maintainer's answer: "not a system limitation, just wrong capture of media keys. Using `MediaKeyTab` fixes that". [#147](https://github.com/AlexPerathoner/SlimHUD/issues/147): "a reasonable level of lag" between changing settings and the bar; a user lowered the poll threshold to 1 % and it "improved but there is still a noticeable delay", at the cost of false triggers from auto-brightness.

### 2.6 MonitorControl and its MediaKeyTap (MIT, 34.5k stars, last push 2026-10-14)

Read at [MonitorControl `7cfe645`](https://github.com/MonitorControl/MonitorControl/tree/7cfe64500d19cbbcbf82121a91c826f658a403bd) and [MediaKeyTap `22293b6`](https://github.com/MonitorControl/MediaKeyTap/tree/22293b608bb9e7072960a2002d77ebbbdb3ba859). It controls external monitors (DDC), so only its key and OSD machinery transfers.

- **MediaKeyTap.** Session tap, head insert, default, mask key-down | system-defined; `return nil` when it handles a key ([MediaKeyTapInternals.swift L112-L158, L183-L199](https://github.com/MonitorControl/MediaKeyTap/blob/22293b608bb9e7072960a2002d77ebbbdb3ba859/MediaKeyTap/MediaKeyTapInternals.swift#L183-L199)). The tap is attached to its own run loop on a private dispatch queue (L172-L180), and the callback then does `DispatchQueue.main.sync { handle }` (L91-L93). It re-enables itself on `tapDisabledByTimeout` (L82-L86). The delegate receives `keyPressed` and `keyRepeat` ([MediaKeyTap.swift L24-L41](https://github.com/MonitorControl/MediaKeyTap/blob/22293b608bb9e7072960a2002d77ebbbdb3ba859/MediaKeyTap/MediaKeyTap.swift#L24-L41)).
- **It leaves the system's own audio path alone when it can.** `updateMediaKeyTap` removes `volumeUp/volumeDown/mute` from the tapped set when the default output `canSetVirtualMainVolume(scope: .output)`, so the system handles those keys natively; only a display whose audio the Mac cannot set (DDC) gets them ([Support/MediaKeyTapManager.swift L148-L186, esp. L169-L179](https://github.com/MonitorControl/MonitorControl/blob/7cfe64500d19cbbcbf82121a91c826f658a403bd/MonitorControl/Support/MediaKeyTapManager.swift#L169-L179)). It also drops the brightness keys when no external display is attached and during sleep.
- **Key repeat.** Per-key `Timer`s: the opposite key's timer is invalidated, and while a key's timer is valid a repeat event is dropped rather than re-applied (L43-L51).
- **Number shown.** Cached preference value, not a read: `stepVolume` computes the next value from `readPrefAsFloat`, issues `writeDDCValues` (async), then draws `OSDUtils.showOsd(... value: volumeOSDValue ...)` in the same function ([Model/OtherDisplay.swift L168-L199](https://github.com/MonitorControl/MonitorControl/blob/7cfe64500d19cbbcbf82121a91c826f658a403bd/MonitorControl/Model/OtherDisplay.swift#L168-L199)).
- **Coalescing.** `writeDDCValues` stores only the newest value per command in `writeDDCNextValue` on a barrier queue and enqueues a global writer that reads that slot and skips if it equals the last sent value ([OtherDisplay.swift L380-L405](https://github.com/MonitorControl/MonitorControl/blob/7cfe64500d19cbbcbf82121a91c826f658a403bd/MonitorControl/Model/OtherDisplay.swift#L380-L405)). Latest wins; a burst of N presses does not mean N slow writes.
- **OSD.** Apple's own OSD, called through private API (`OSDManager.showImage`) or, on macOS 26 and 27, the XPC connection described in section 1. Draw requests are moved to the main thread (OSDUtils.swift L88-L94).

## 4. What the fast ones have in common

Criterion: no project here was measured. These are mechanics shared by the designs whose code or changelog is built around not blocking on the device, set against the two that visibly do (SlimHUD, and read-back-driven mew-notch). Where Isla is mentioned it is from `Sources/IslaKit/Services` at the working-tree commit `b1ea653`, for comparison only.

1. **The number on screen is computed from the key, not read from the device.** boring.notch draws `target` right after the write call (VolumeManager.swift L43). Atoll draws the value it just wrote (SystemMediaControllers.swift L233-L247). volumeHUD draws the quantized expected value "not the actual read-back" (MediaKeyInterceptor.swift L546-L549). MonitorControl draws the cached value in the same function that queues the write (OtherDisplay.swift L168-L199). The two that wait for the device or a poll are the ones with delay reports: SlimHUD (AppleScript read after the key plus a 0.2 s poll; #86, #147) and mew-notch (listener, then main-thread hop, then notification). Apple's header says the write is not complete until the listener runs. *Isla:* `SystemLevelApplier.applyVolume` returns the stepped level it just wrote ([SystemLevels.swift L565-L596](../../../Sources/IslaKit/Services/SystemLevels.swift)), the same shape.
2. **The tap callback does no device work and returns at once.** Every interceptor that states a rule states this one: Atoll's "must return promptly or macOS disables it", MediaKeyTap's own thread and `main.sync` of only the handler, boring.notch and volumeHUD's `Task { @MainActor }`, and re-enable-on-`tapDisabledByTimeout` in MediaKeyTap, Atoll, mew-notch and volumeHUD. mew-notch is the exception that writes CoreAudio inside the callback. Tap location (HID or session) is not what separates them: both appear among the working ones. *Isla:* session tap on its own `Thread` ([MediaKeyTap.swift L158-L221](../../../Sources/IslaKit/Services/MediaKeyTap.swift)).
3. **Work happens somewhere other than the main thread, or the main thread is the only thing waiting.** Counter-example in the set: boring.notch and Atoll run the volume read and write on main (boring.notch's open PR #1540 is about stalls on slow devices). The designs that explicitly avoid main: MonitorControl (DDC on barrier queues, OSD hop only for drawing), Atoll's listener queue and sound queue. *Isla:* writes on `com.ctimothe.isla.levels` at `.userInteractive`, drawing via a latest-wins mailbox (`LatestReadingMailbox`, [MediaKeyHUD.swift L940-L982](../../../Sources/IslaKit/Services/MediaKeyHUD.swift)).
4. **Held keys collapse to the newest intent instead of queueing.** MonitorControl: one "next value" slot per command, skip if equal to the last sent (OtherDisplay.swift L380-L405). Atoll brightness: `pendingAdjustTarget` stepped from the in-flight target, one main hop (SystemMediaControllers.swift L720-L728). boring.notch PR #1540 (open): one accepted write with coalesced newer intent while acknowledgement is pending. Key repeat in MonitorControl is also gated by per-key timers (MediaKeyTapManager.swift L43-L51). None of these steps a held key from a fresh device read each repeat. Atoll's volume and boring.notch's volume do, and they have no accumulator.
5. **Steps are taken from a remembered target, with a read only when it is stale or disagrees.** volumeHUD: continue from `requestedVolume` while the device reports the previous request's physical result (L489-L501). Atoll: per-device remembered level, refuses to step from an unconfirmed one (L165-L168, L233-L247), and for brightness never queries inside the key path. MonitorControl: its own cached value. *Isla:* brightness trusts a level it wrote or read for 1.5 s (`levelTrustedFor`, SystemLevels.swift L441, L645-L662); the volume path steps from `volumeState`, a cache refreshed by listeners ([L565-L596, L603-L620](../../../Sources/IslaKit/Services/SystemLevels.swift)).
6. **One write selector, chosen up front.** `VirtualMainVolume` (`'vmvc'`) is what mew-notch and volumeHUD use for both read and write, and what Atoll falls back to ("the property macOS's own volume UI works through"); boring.notch and Atoll's first try is per-element `VolumeScalar`, with up to four sequential `HasProperty`/`GetPropertyDataSize`/`GetPropertyData`/`SetPropertyData` calls per element (VolumeManager.swift L331-L363). MonitorControl asks `canSetVirtualMainVolume` and steps aside when true. The shorter the sequence of HAL round trips per press, the less there is to stall. *Isla:* virtual main first, main scalar next, per-channel last ([SystemVolume.swift L116-L129](../../../Sources/IslaKit/Services/SystemVolume.swift)); a settable check precedes each write (L228-L237).
7. **The key is swallowed; the system OSD is only additionally frozen by those that must.** boring.notch, volumeHUD, mew-notch and MediaKeyTap swallow and do nothing else. Atoll adds `SIGSTOP` because it observed the CoreAudio write waking the helper; SlimHUD freezes because it does not swallow. Freezing costs a fork per press in Atoll (guarded by a 0.6 ms pid lookup) and a catalogue of side effects (#568, #574, #608). The OSD-process route is also tied to a helper whose role Apple changed in 26 and 27.
8. **Feedback sound is off the critical path.** Atoll: serial queue, 80 ms minimum between plays. boring.notch plays before the volume change on the main actor (L204-L207), the only one in the set that does.
9. **External changes come from property listeners on the volume, mute and default-device objects, not a poll.** boring.notch, Atoll, mew-notch, volumeHUD. SlimHUD polls at 0.2 s and observes a distributed notification. Atoll delivers them on a private serial queue (L69); boring.notch uses a NULL queue (HAL thread, header L389) then hops to main. volumeHUD keeps a timestamp so the listener does not redraw a change it caused (L543-L544); boring.notch has no such guard (its own write triggers a full re-read).
10. **The pop-up is a state flip with a restartable linger.** boring.notch `.smooth` + a cancel-and-restart 1.5 s task; SlimHUD `show()` then `dismiss(delay: 1.5)`; Isla 1.5 s. None starts the draw behind an async step.

### What I could not establish

- Any measured latency from key-down to first drawn frame, for any app, ours included.
- Which process draws the OSD on macOS 27.0 versus 27.2, beyond the MonitorControl maintainer's account of Control Center and a change in 27.2.
- Whether swallowing the key is enough to keep the OSD down on 27.x when the volume is set by CoreAudio: Atoll's comment says a CoreAudio write alone wakes the helper, but it is the one project that says so and I did not test it.
- Whether PR #1540's coalescing is faster on real hardware; its author says it is untested on AirPods and DACs.
- The paid apps' mechanics: none of them publishes any.
